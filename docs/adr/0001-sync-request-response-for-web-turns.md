# Web 版回合處理：同步請求-回應，不做即時串流

網頁採用同步請求-回應，每個 AI 回合分開請求，不使用即時串流。`/api/new_game` 立即回傳初始牌桌，不呼叫 AI；`/api/move` 只驗證並套用真人這一手，回傳事件與當下狀態。前端先播放這一手，再透過 `/api/ai_turn` 每次取得一個 AI 回合，播放完才請求下一回合，直到輪到真人或遊戲結束。純觀戰使用同一流程；`/api/spectate` 保留為僅限觀戰的單回合入口。

原本真人模式在同一個 request 中算完所有後續 AI 回合才回傳，讓玩家必須等待多次模型決策才看見第一手 AI 出牌。改成逐回合請求後，每個決策完成即可顯示，不需增加背景執行緒或推播連線。

考慮過的替代方案：用背景 thread 跑遊戲迴圈、人類出牌透過 queue 餵入，搭配 SSE/WebSocket 把每個 AI 回合即時推播給前端，讓畫面在 AI 決策當下就更新。這個方案的即時感更好，但需要引入執行緒間的併發狀態管理、連線斷開重連等新的複雜度——而目前的使用情境是單人在本機開一個瀏覽器分頁玩，沒有多人即時對戰的需求，因此判斷不值得為此增加複雜度。

若未來需要真正的多人即時對戰（多個瀏覽器同時看到同一局進度、不能等一整批算完才更新），這個決定需要重新評估，屆時很可能要換成背景 thread + 推播的架構。
